
## 10 个元素的插入排序耗时受运行频率影响，LSR 增加索引维护

`slice::sort_unstable_small_random` 每次克隆并排序同一组 10 个 `u64`。两端进入同一套插入排序实现。当前最明确的时间差因素是运行频率：ARM 约 2.9 GHz，x86 的频率在本轮测试中明显变化，原测试的时间差也随之变化。LSR 还会引入额外的索引维护，但关闭它没有得到稳定覆盖各场景的收益。

### 接口、输入和基线

| 接口或操作 | 对应 benchmark | 实际执行内容 |
|---|---|---|
| `[u64]::sort_unstable()` | `slice::sort_unstable_small_random` | 10 个元素，插入排序 |
| `Vec<u64>::clone()` 及释放 | 同上 | 每次分配 80 字节，复制输入，排序后释放 |
| `[u64]::sort_unstable()` | `sort_unstable_small_ascending`、`sort_unstable_small_descending` | 同长度的有序和逆序对照 |

原宏和生成器保持原样。核心调用为：

```rust
let v = gen_random(10);
b.iter(|| v.clone().sort_unstable());
```

随机数由 `XorShiftRng` 使用种子 `[0, 1, …, 15]` 生成，只在计时前生成一次。每轮都复制同一组数据。该输入需要 26 次比较、18 次右移；这些数字通过计数比较器和独立的插入操作计数核对。

完整路径为 `sort_unstable → sort::unstable::sort → insertion_sort_shift_left(v, 1, ...) → insert_tail`。长度不超过 20 时使用此路径。输入长度 10 不进入快速排序分区，也不进入堆排序。实际汇编保留了排序循环。

本次使用同一 rustc 1.99.0-dev / LLVM 23.1.0 为两个目标编译，默认 CPU 特性。标准库使用冻结 baseline sysroot，远程当前排序目录的全部 `.rs` 文件与冻结源码逐文件一致。源码 HEAD 为 `dc55da5cca14a0aa773ecb7a0459756260b2ee5c`，内容校验和另行保存。ARM 为远程 HiSilicon 服务器 CPU 52；x86 为 i7-12700 的 P 核 CPU 12。内核、libc、SMT、频率条件及实际库文件校验和见证据目录。

| 原始配置的不同测量轮次，中位数 | ARM ns | x86 ns | ARM/x86 | ARM / x86 频率近似值 |
|---|---:|---:|---:|---:|
| 第一组，五次 | 31.57 | 26.05 | 1.212 | 2.89 / 3.68 GHz |
| 相关 benchmark 复测，三次 | 31.46 | 25.24 | 1.246 | 2.90 / 3.75 GHz |
| LSR 对照中的默认配置，五次 | 31.55 | 29.98 | 1.052 | 2.90 / 3.13 GHz |

频率近似值为用户态 cycles 除 task-clock；libtest 长测试中的启动及内核时间占比较小。它用于描述本轮运行条件，不能代替锁频。x86 有后台负载、同核 SMT 线程活动和频率变化，当前数据不支持给出固定的跨机耗时比例。第一组 ARM 原始范围为 31.44–52.79 ns，后续相关 benchmark 复测为 31.44–31.47 ns；全部样本均保留，没有只选最快结果。

历史 `base.tsv` 的 31.44 / 19.81 ns 属于另一套构建，与本轮数据分开。

### 原因：较低的运行频率增加每个周期对应的时间

将同一输入放入独立驱动，分别测量克隆、预分配缓冲区内排序和完整操作：

```rust
#[inline(never)]
#[unsafe(no_mangle)]
pub fn sort_u64(v: &mut [u64]) {
    v.sort_unstable();
}

#[inline(never)]
#[unsafe(no_mangle)]
pub fn clone_sort(v: &Vec<u64>) {
    v.clone().sort_unstable();
}
```

完整可运行复现为证据目录的 `arm/probes.rs`，从命令行读取长度、分布和次数，避免长度在调用方被固定。`full 10 original 1000000` 重复克隆、排序、释放；`sort 10 original 1000000` 在预分配缓冲区内恢复输入并排序；`clone 10 original 1000000` 测克隆与释放。`black_box` 的位置及数据恢复均在驱动源码中。

| 独立驱动，默认配置，三次中位数 | ARM ns / cycles | x86 ns / cycles |
|---|---:|---:|
| 克隆并释放 10 个 u64 | 15.61 / 45.72 | 12.39 / 46.29 |
| 恢复输入并排序 | 21.18 / 62.02 | 19.69 / 70.82 |
| 克隆、排序、释放 | 40.07 / 116.34 | 30.92 / 114.04 |

完整驱动中，两端周期数接近，ARM 耗时约高 30%。较低的运行频率解释了其中的主要时间差。单独排序对照没有显示与纳秒差距相应的 ARM 周期劣势。

原 benchmark 的热点还包括分配释放：ARM 的 `malloc`、`_int_free`、`cfree` 合计约 41%，x86 的 `malloc`、`cfree` 合计也约 41%。这说明分配释放是本项重要的计时组成。80 字节克隆对照的周期数接近，本次没有证据将该项的主要周期差距归为 ARM 分配器更慢。此前 Vec 的 800 字节结果不能转用于这里。

这些独立驱动有额外调用和 black_box，恢复输入的方式也不同；其周期数只在同一驱动中跨平台比较。不能将三个分项相加后直接扣减原 benchmark 的时间。

### 原因：LSR 将递减指针改为基址加位移，增加索引维护

插入排序向左移动游标，逐个比较并搬移元素。原实现直接维护指针。下面是实际 `loop-reduce` 前后 IR 的关键部分，省略元数据和外围块，数值名称保留自编译器输出。

```llvm
; LSR 前：直接维护向左移动的指针
24:
  %25 = phi ptr [ %26, %22 ], [ %15, %21 ]
  %26 = getelementptr inbounds i8, ptr %25, i64 -8
  %27 = load i64, ptr %26, align 8
  %28 = icmp ult i64 %16, %27
  br i1 %28, label %22, label %29
22:
  store i64 %27, ptr %25, align 8
  %23 = icmp eq ptr %26, %0
  br i1 %23, label %29, label %24
```

```llvm
; LSR 后：位移循环变量，加载和写入地址由基址与位移重建
27:
  %28 = phi i64 [ %15, %23 ], [ %25, %24 ]
  %29 = getelementptr i8, ptr %0, i64 %28
  %30 = getelementptr i8, ptr %29, i64 -8
  %31 = getelementptr i8, ptr %0, i64 %28
  %32 = getelementptr i8, ptr %31, i64 -16
  %33 = load i64, ptr %32, align 8
  %34 = icmp ult i64 %18, %33
  br i1 %34, label %24, label %36
24:
  store i64 %33, ptr %30, align 8
  %25 = add i64 %28, -8
  %26 = icmp eq i64 %25, 8
  br i1 %26, label %35, label %27
```

ARM 最终生成 `add 地址, 基址, 位移` 再加载，并在外层同时更新尾指针和字节位移。关闭 LSR 后保留递减指针，外层不再单独更新位移，内层增加其他指针维护指令。

```asm
// ARM 默认配置：内层使用基址和字节位移
add  x12, x0, x13
ldur x14, [x12, #-8]
cmp  x11, x14
b.hs insert
subs x13, x13, #8
str  x14, [x12]
b.ne inner

// ARM 关闭 LSR：内层使用递减指针
mov  x12, x11
ldr  x13, [x12, #-8]!
cmp  x10, x13
b.hs insert
cmp  x12, x0
str  x13, [x11]
mov  x11, x12
b.ne inner
```

x86 默认配置可用 `mov -8(base,index), reg` 直接表达相应加载。关闭 LSR 后改用递减指针，并增加指针与边界比较。两端都有循环表示变化。

固定次数原查询驱动中，关闭 LSR 后 ARM 每次操作从 463.11 降到 446.11 条指令，x86 从 378.30 降到 364.30 条。此结果证实 LSR 增加了该输入下的动态指令数。

| 原 benchmark 的 LSR 配置对照，五次中位数 | ARM | x86 |
|---|---:|---:|
| 默认配置 | 31.55 ns | 29.98 ns |
| `-Cllvm-args=-disable-lsr` | 30.61 ns | 27.99 ns |
| 耗时变化 | -3.0% | -6.6% |

减少指令没有在全部场景中减少耗时。以下数据来自另一次交错测量的独立驱动，和上表分开：

| 长度、分布及计时范围 | ARM 默认→关闭 LSR | x86 默认→关闭 LSR |
|---|---:|---:|
| 10，原始随机，恢复输入并排序 | 21.11→21.44 ns | 22.24→19.70 ns |
| 10，原始随机，克隆加排序释放 | 47.66→44.30 ns | 36.15→37.56 ns |
| 10，有序，恢复输入并排序 | 9.43→9.70 ns | 10.64→12.74 ns |
| 10，逆序，恢复输入并排序 | 30.80→31.26 ns | 30.06→26.38 ns |

该选项改变应用编译单元内多个循环及代码布局，收益不能全部归给减少的索引维护。当前只能确认额外指令及上述配置结果，不能将 LSR 定为整个 ARM/x86 时间差的主因。

### 代码地址影响固定次数驱动，不能转记为原测试收益

第一组固定次数驱动中，将 `-unroll-threshold` 和 `-unroll-partial-threshold` 设为 0 后，ARM 周期从 134.57 降到 96.28，误预测从 1.52 次降到约 0.002 次；指令数与分支数保持相同。原 libtest 测试的中位数则为 31.57→31.47 ns。两种驱动的效果不同。

进一步对原目标文件重命名排序函数所在段，并重新链接到 `0x1000000 + offset`，offset 覆盖 0–240、步长 16，原 benchmark 和接口源码均不变。ARM 已校验：除链接重定位字段外，目标函数的指令字节一致，其他函数地址一致。

ARM 的完整 libtest 测试在各位置的三次中位数为 31.45–32.14 ns；固定次数驱动为 36.06–45.94 ns，误预测也随位置变化。这证明固定次数驱动对代码地址更敏感，其明显改善不能用作原测试的同等收益证据。具体预测器内部冲突尚未确定。

x86 链接器在本轮扫描中还移动了其他函数，因此其数据只保留为整体布局对照，不用于单函数地址归因。该检查结果及所有原始运行均保留。

### 修改方法与适用范围

| 已确认问题 | 对应方法 | 验证状态和限制 |
|---|---|---|
| ARM 运行频率较低，纳秒比较受 x86 运行条件影响 | 同时比较时间和周期，控制频率、SMT 竞争和后台负载 | 无已验证的接口源码修改；本轮不能给出固定的硬件耗时比例 |
| LSR 增加字节位移维护 | `-Cllvm-args=-disable-lsr`；继续查找能稳定保留适当指针循环的源码表示 | 原 benchmark 有小幅配置收益，多个输入存在退化。当前源码已经使用指针，直接改成指针写法不足以保证生成代码；无已验证的源码绕过方法 |
| 固定次数驱动受代码地址影响 | 对基线和变体检查实际代码并扫描多个地址，再回到原 libtest 测试 | 已确认 ARM 探针的位置敏感性；不作为排序接口优化方法 |

其余诊断选项在原测试中的 ARM 中位数：`-aarch64-select-opt=false` 为 31.47 ns，`-aarch64-enable-early-ifcvt=false` 为 32.48 ns，`-no-stack-coloring` 为 32.10 ns，`-aarch64-enable-ldst-opt=false` 为 31.46 ns，展开阈值置零为 31.47 ns；同轮默认配置为 31.57 ns。它们没有提供明确的完整测试收益。select 和 early-ifcvt 影响分支与条件执行的取舍，栈及加载写入选项影响布局与配对，展开阈值影响代码体积和循环控制；实际结果及 x86 适用配置见 `target-summary.csv`。

插入排序的退出条件在 LLVM IR 中已经是 `br`，实际执行“继续搬移或结束插入”的判断。本项没有 select 被改成不可预测分支的证据，也没有 x86 有 SIMD 而 ARM 缺少 NEON 路径的源码差异。

### 覆盖与复现

基线运行 22 个原始排序 benchmark，各三次。独立驱动覆盖长度 0、1、2、5、10、16、20、21、32，分布包括固定随机、有序、逆序、全相同和四值重复，分别测预分配缓冲区内排序与完整克隆排序。默认/展开阈值置零、默认/关闭 LSR 两组各包含 90 个成对性能场景，每场景三次，另有克隆、恢复输入和轮换输入对照。正确性检查覆盖 0–64 各长度、五种分布，并对照稳定排序及带计数的比较器。性能矩阵限于 u64；其他类型及自定义比较器的性能没有覆盖。

两端固定 CPU，关闭 ASLR；perf 父进程也固定，x86 使用 `cpu_core` 事件。四个硬件事件运行比例均为 100%，全部测量无 CPU 迁移。记录了上下文切换、主次缺页、task-clock 和原始输出。x86 部分进程出现主缺页；进程级记录不足以精确定位到计时窗口，不能将这些样本当作排除了系统干扰的硬件延迟测量。最初有一次 x86 相关测试与探针重叠，已完整重跑两组，重叠轮次单独保存在 pilot 文件中，不进入正文和汇总表。

证据目录：[`analysis/data/sort-unstable-small-random-20261106/`](analysis/data/sort-unstable-small-random-20261106/)。完整源码、依赖与构建命令、真实前后 IR、汇编、原始计数和范围均已保存。`README.md` 说明复现步骤与测量范围；`*-summary.csv` 保存各组中位数及范围，`layout-validation.json` 保存地址控制的检查结果。

本次没有修改原 benchmark 或标准库接口。当前结论是运行频率构成明确的时间差因素，LSR 引入了额外索引维护；尚无覆盖相关场景的通用接口修复。
