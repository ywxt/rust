# 元组比较结果的生成与打包增加 ARM 开销

`tuple::bench_tuple_comparison` 每轮随机选择两个 `(&str, usize)`，返回 `<`、`<=`、`>`、`>=` 四个结果。原 benchmark 的四个关系表达式保持不变。本次已定位结果生成、打包及条件分支的成本；此前通过减少比较调用、改用 `cmp` 得到的数据属于调用端改写诊断，尚无已验证的接口修改方案。

## 基线和原因

2026-11-05，ARM 为 HiSilicon 920B、CPU 52，x86 为 Intel i7-12700、CPU 12。两端使用现有 stage1 的 rustc 1.101.0-dev、LLVM 23.1.4，`-O`，默认目标特性。ARM glibc 2.38，x86 glibc 2.42。编译器提交号为 `unknown`；分析源码目录提交为 `8fcaaf4c3fe47544c8d857e421ec258e7b06be96`，二者的对应关系未确认。

| 完整基准，ns/次 | ARM | x86 |
|---|---:|---:|
| 现有 corebenches，5 轮中位数 | 11.40 | 6.47 |
| 同样输入和 libtest 流程重建，采用原构建记录的 rustflags，3 轮中位数 | 11.36 | 6.46 |

重建基线范围为 ARM 11.35–12.58 ns，x86 6.41–6.49 ns。后续对照的 ARM 基线约 11.40–11.48 ns。完整耗时比约 1.76；长循环的计数与时间对应运行频率约为 ARM 2.9 GHz、x86 4.5 GHz，时间比不能直接当作周期比。

| 成因 | 实际行为及 ARM 成本 | 接口和 benchmark | 对应方法 |
|---|---|---|---|
| LLVM 对四种关系分别生成结果，再打包为四字节 | ARM 为多个布尔值生成 `cset`，随后再次比较布尔值，用 `csel` 选取 `256`、`65536`、`16777216`，最后 `orr`。调用端显式写出互补关系后，独立循环每轮少 11 条指令；该结果不能计为接口优化收益 | `(&str, usize)` 的关系比较；`tuple::bench_tuple_comparison` | 无已验证接口修改方法；两种调用端改写仅保留为诊断 |
| LLVM 保留字符串相等时的条件分支 | 两端原基准都按字符串是否相等分支，约 1/6 输入进入整数比较。ARM 的 `cmp` 改写仍有该分支；提高 PHI 转 select 的成本阈值后，改写版本生成无分支选择，随机循环的预测失败显著减少 | 同上 | 无已验证接口修改方法；该选项只在改写调用端后显著改善，原始四关系版本未改善 |
| libc 的 27 字节比较路径不同 | ARM 先比较前 16 字节，再比较末尾 16 字节；六个输入的前 22 字节相同，前一段始终无法确定大小。x86 常见路径使用 32 字节 AVX2 比较和字节掩码；接近页尾时采用两段 16 字节路径。调用、加载、比较及取结果的指令不同 | `str`/字节切片比较最终调用 `memcmp`；同一 benchmark | 无已验证修改方法；尚未独立量化该路径造成的完整耗时差 |

两端均只调用一次 `memcmp`，LLVM 已合并四次关系运算的字符串比较。这里没有“四次字符串扫描”的问题。Rust 元组比较与 `str` 比较的源码路径相同；本次未发现 Rust 源码中 x86 有 SIMD、ARM 缺少 NEON 的平台分支。

六个字符串均为 27 字节。选择同一条目时字符串及整数均相等，概率约 1/6；其余输入由字符串决定结果。原基准没有覆盖“字符串内容相同、整数不同”。随机数生成和两次 `choose` 也在计时内。

## 结果打包为何增加指令

最小复现保留相同类型和四个返回结果：

```rust
fn compare(x: &(&str, usize), y: &(&str, usize)) -> [bool; 4] {
    [x < y, x <= y, x > y, x >= y]
}
```

可运行程序见 [leaf.rs](common/leaf.rs) 和 [compare.rs](common/compare.rs)。`leaf_original` 为独立调用，完整基准仍以内联闭包执行；两种上下文的分支选择有差异。

实际 LLVM IR 把三个高位字节表示为条件选常量，节选如下；完整内容见 [ARM IR](arm/leaf-full.ll)：

```llvm
%_0.sroa.4.0.insert.shift.i = select i1 %val3.sroa.0.0.i.v, i32 16777216, i32 0
%_0.sroa.3.0.insert.shift.i = select i1 %val2.sroa.0.0.i.v, i32 65536, i32 0
%_0.sroa.2.0.insert.shift.i = select i1 %val1.sroa.0.0.i.v, i32 256, i32 0
```

ARM 实际汇编在布尔值已生成后，又执行以下打包操作：

```asm
cmp   w11, #0
mov   w11, #16777216
csel  w11, w11, wzr, ne
cmp   w10, #0
mov   w10, #65536
csel  w10, w10, wzr, ne
cmp   w9, #0
mov   w9, #256
csel  w9, w9, wzr, ne
```

x86 使用 `setcc` 生成布尔字节，再移位、合并为四字节结果。调用端改写诊断可以减少上述打包工作；它尚未证明对应接口能够在保持调用端不变时消除该成本。完整基准的原始汇编见 [ARM](arm/prebuilt-tuple-0.aarch64.asm) 和 [x86](x86/prebuilt-tuple-0.x86_64.asm)。

## 接口修改范围与当前结论

对应实现位于 `library/core/src/tuple.rs`：元组的 `PartialOrd::{lt, le, gt, ge}` 调用 `lexical_ord!`，前面字段经 `__chaining_*` 决定短路或继续，最后一个字段调用对应关系方法。字符串字段继续进入 `str`、字节切片比较及 `memcmp`。

接口改动应保留原 benchmark 中的 `[x < y, x <= y, x > y, x >= y]`、随机取样、输入和计时范围。把四次关系调用改为两次，或改为一次 `Ord::cmp`，均发生在调用端，不能由某一个关系方法直接替换。通用接口还需保持不可比较值、字段短路、panic 和自定义比较行为。

当前未发现原 benchmark 的正确性或计时错误，没有修改 benchmark 的依据。后续接口候选须在接口实现内验证，随后使用未经修改的原 benchmark 和其他适用场景复测。当前结论为：**无已验证接口修改方法。** 结果打包涉及内联后的调用端四字节数组构造，需要继续区分接口表达方式能否改善，以及 LLVM 是否需要改进；现有调用端诊断不能代替该验证。

## 调用端改写诊断

本节程序改变了 benchmark 的比较表达式，只用于区分生成代码的成本，不属于接口修改，也不能作为原 benchmark 的优化结果。

诊断一，只计算两种关系：

```rust
fn compare_two(x: &(&str, usize), y: &(&str, usize)) -> [bool; 4] {
    let lt = x < y;
    let gt = x > y;
    [lt, !gt, gt, !lt]
}
```

对于 `(&str, usize)` 的全序关系，`<=` 与 `>` 互补，`>=` 与 `<` 互补。LLVM 因此减少整数关系比较和结果选择，ARM 的改写探针也消除了字符串相等时的条件跳转。x86 同时增加了无条件整数比较、条件移动和补集打包，改写探针出现小幅回退。

诊断二，比较一次并返回三个固定数组之一：

```rust
fn compare_match(x: &(&str, usize), y: &(&str, usize)) -> [bool; 4] {
    match x.cmp(y) {
        std::cmp::Ordering::Less => [true, true, false, false],
        std::cmp::Ordering::Equal => [false, true, false, true],
        std::cmp::Ordering::Greater => [false, false, true, true],
    }
}
```

该写法把分别构造四个布尔值改为取一个完整的四字节结果。当前编译器生成结果表查找。ARM 默认编译仍保留字符串相等时的分支。

| 原构建 rustflags，同输入的 libtest 诊断探针 | ARM ns/次 | 相对 ARM 基线 | x86 ns/次 | 相对 x86 基线 |
|---|---:|---:|---:|---:|
| 四种关系分别计算 | 11.36 | 基线 | 6.46 | 基线 |
| 调用端诊断：两种关系及补集 | 8.84 | −22.2% | 6.64 | **+2.8%** |
| 调用端诊断：`cmp` 后返回固定数组 | 10.27 | −9.6% | 5.72 | −11.5% |
| 调用端 `cmp` 诊断 + PHI 成本阈值 16 | 8.11 | −28.6% | 5.74 | −11.1% |

前两项调用端改写只针对当前具体类型与返回需求。含 NaN 的 `PartialOrd`、自定义比较器及比较调用有副作用的类型，需要重新判断语义；以上结果不能用于宣称标准库所有元组比较都获得优化。

## 随机条件分支与 LLVM 选项

对照命令在原有 rustflags 上增加：

```text
-Cllvm-args=-two-entry-phi-node-folding-threshold=16
```

当前 LLVM 帮助说明该选项控制把两入口 PHI 折叠为 select 时允许提前执行的最大指令成本，默认值为 4。它允许先计算整数关系，再按字符串结果选择，减少随机分支。

默认 `cmp` 版本在字符串相等时跳转到整数比较。阈值 16 下，对应 IR 已改为无分支选择，实际节选：

```llvm
%26 = icmp eq i64 %spec.select.i.i, 0
%_28.i.i = load i64, ptr %27, align 8, !alias.scope !152, !noalias !155
%_29.i.i = load i64, ptr %28, align 8, !alias.scope !155, !noalias !152
%29 = call i8 @llvm.ucmp.i8.i64(i64 %_28.i.i, i64 %_29.i.i)
%ordering.sroa.0.0.i.i = select i1 %26, i8 %29, i8 %25
```

完整前后 IR 见 [默认](arm/harness-fullflags.ll)、[阈值 16](arm/harness-options-two16.ll)。原始四关系版本的对应分支已经存在于优化后的 IR；关闭 `aarch64-select-opt` 未消除它，不能将该分支归因于 ARM select-optimize。

独立固定迭代循环保留原始随机种子和两次取样，每个变体每轮 1000 万次，5 轮交错取中位数。以下计数用于验证指令与分支变化；该循环的内联上下文与 libtest 不同，耗时不替代完整基准：

| 变体 | ARM cycles/次 | ARM 指令/次 | ARM 预测失败/次 | x86 cycles/次 | x86 指令/次 | x86 预测失败/次 |
|---|---:|---:|---:|---:|---:|---:|
| 原始四关系 | 29.40 | 94.11 | 0.0014 | 33.05 | 113.80 | 0.1703 |
| 两关系及补集 | 25.62 | 83.11 | 0.0014 | 30.73 | 108.80 | 0.1703 |
| `cmp` 后返回固定数组 | 29.02 | 72.95 | 0.1818 | 26.78 | 91.47 | 0.1715 |
| `cmp` + 阈值 16 | 23.44 | 77.11 | 0.0014 | 27.13 | 90.84 | 0.1713 |

ARM 的 `cmp` 默认版本指令较少，但新增的随机条件分支抵消了大部分收益。提高阈值后，指令略增、预测失败大幅减少，周期下降。x86 的同一诊断选项没有带来相应收益。

其余选项也做了单项对照：提高 `phi-node-folding-threshold`、提高 `bonus-inst-threshold`、二者与上述选项组合，以及关闭目标平台的 select/cmov 转换。ARM 原始版本约 11.40–11.42 ns，单独提高这些阈值未改善原始四关系版本；该选项对 `cmp` 调用端探针有效，不能将该收益转记到保持原调用端的接口实现。所有选项和原始结果见 [选项实验](arm/options.aarch64.json)。

这些选项作用于整个编译单元，可能使可预测分支执行更多无条件计算，并增加加载、寄存器占用和代码体积。它们属于诊断结果，尚无全程序或其他目标平台的收益验证。

## 适用场景、回退和测量条件

性能覆盖了 42 组预选输入：长度 0、1、7、8、15、16、27、31、32、33、64、128、1024；首字节和末字节不同、内容相同但地址不同、长度不同、字符串相同且整数不同，以及约 1/6、1/2 的字符串相等比例。每组 5 轮，输入顺序周期性重复，方向交替；这些分支较容易预测。另有 1444 对语义检查，性能矩阵的 10752 对输入也逐对校验四个返回结果。

| 场景及单位 | ARM 原始 | ARM 两关系 | ARM `cmp` | x86 原始 | x86 两关系 | x86 `cmp` |
|---|---:|---:|---:|---:|---:|---:|
| 27 字节，末字节不同，ns/次 | 8.011 | 6.155 | 5.497 | 3.677 | 3.141 | 2.248 |
| 27 字节，内容相同、整数不同，ns/次 | 8.001 | 6.164 | 5.379 | 3.488 | 2.705 | 2.219 |
| 1024 字节，末字节不同，ns/次 | 33.498 | 32.485 | 31.601 | 12.917 | 12.801 | 12.211 |

两种调用端改写在该诊断矩阵的中位数均下降；1024 字节输入下部分改善不足 2%，不能据此判定稳定收益。x86 的两关系调用端探针在随机取样下回退 2.8%。这些数据不提供接口优化收益的证据。

阈值 16 与默认 `cmp` 相比，ARM 的 42 组中有 28 组回退超过 2%，最大为 16 字节末尾不同：4.023 → 4.309 ns，约 +7.1%。x86 最大回退为 64 字节首字节不同：2.184 → 2.231 ns，约 +2.1%。全部逐场景结果见 [性能矩阵](scenarios.md)。该全局选项的收益受输入分布和调用上下文影响。

测量另核对了以下条件：

- 原构建使用 `-Cprefer-dynamic`。x86 单独加入该选项即可将独立重建基线从约 7.8 ns 恢复到约 6.3 ns；它改变链接方式及生成代码上下文，不能把两种构建的时间差记为源码收益。
- 函数对齐取 16、32、64 字节，ARM 两关系版本均约 8.81–8.83 ns，`cmp` 约 10.23–10.35 ns；x86 两关系均约 6.48–6.54 ns、`cmp` 约 5.69–5.77 ns。调用端诊断的收益和回退方向保持一致。该检查只覆盖这些代码布局，数据地址和跨页位置未做穷举。
- PMU 事件运行占比为 100%。保留了 task-clock、上下文切换、迁移与缺页原始记录；计数覆盖进程启动，个别启动记录有 major fault，中位数为 0。计时由程序内部循环或 libtest 执行，未用整个进程的墙钟时间替代每轮时间。
- 现有二进制采样中，ARM 的 libc `memcmp` 约占 33.77%，`memcmp@plt` 约 6.45%；x86 的 `__memcmp_avx2_movbe` 约 25.90%。采样确认比较路径属于热点；两端占比不能直接相减计算耗时差。

全部实验代码、命令、IR、汇编、原始记录及环境信息见 [复现说明](README.md)。本次未修改标准库生产代码。
